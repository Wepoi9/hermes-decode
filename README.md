# Hermes Decode（Desktop 専用デコード速度プラグイン）

Hermes Desktop のステータスバーに、ただいまのモデルのデコード速度だけを一行で表示する、単一パッケージの Hermes プラグインです。集計は**セッション**（と実接続先）単位で別々に保たれ、フォーカス中のセッションの直近 10 回の計測値だけを保持します。セッションを切り替えると表示の参照先も切り替わり、新しいセッションは最初の呼び出しが完了するまで `—` です。表示は「いま使っているセッション」に属する直近の有効サンプルの値です（他のセッションの値は出しません。一つのセッションの計測が 2 つ以上の接続先またぎで混在するときは判別不能なので、使っていない可能性のある接続先の速度を拾わず `—` を出します。モデルを切り替えるとそのセッションのデコード履歴をリセットするので、直前のモデルの計測を混ぜません）。表示値は完了済み呼び出しの計測結果であり、生成中のリアルタイム速度ではありません。

- 速度の定義: 直近 10 回の**有効な**モデル応答につき、出力トークン数を合計し、その応答が占めたデコード秒数を合計して割ります（`Σ output tokens ÷ Σ decode seconds`）。速度の平均を取りません。
- 表示は整数 `tok/s`（例 `↑ 105 tok/s`）。未計測のときは値を出しません（`—`）。
- 計測は「そのリクエストで最初に実データ delta を受信した瞬間 → 終端フレームを処理し終えた瞬間」です。ストリーミング応答限定で、待機・工具実行・プロンプト処理・再試行・中断・失敗／不完全終端を除外します。ツール引数・reasoning の delta はデコード生成の開始点なので、その生成時間は窓に含めます（Codex 側は実データを伴う delta だけを数え、引数なしの announce 通知は窓を開けません）。窓を閉じられるのは確定したクリーンな完了終端だけで、failed・incomplete 終端は `None`（未計測）のままです。
- データ保存は原則メモリ内のみ。履歴は（セッション, 実接続先）単位の窓（セッション横断では共有されない直近 10 件）に保ち、窓の保持は少数（LRU 8 窓、セッションのモデル管理台帳も同じ上限で頭打ち）に保ち、無制限に増やしません。永続 DB・ログ・外部 API サーバー・WebSocket サーバー・バックグラウンドポーリングは使いません。窓の読み書きは小さなロックで一貫性を保ち、同時進行の API 呼び出しとプラグイン再読込の両立を確認します。

## 構成

```
plugin.yaml                 # 本体フック post_api_request のみ宣言（ツールは登録しない）
__init__.py                 # 集計（直近10件の窓・合算比）と Desktop へのイベント通知
desktop/plugin.js           # Desktop 表示（STATUSBAR_AREAS.right の 1 項目のみ、フォーカス中セッション追従）
patches/decode-hook.patch        # 本体が上流で計測を受け付けるまでの一時的な計測配線（上流 main 基準）
patches/decode-hook-v0.22.2.patch # 公開済み v0.22.2 を動かしている間の計測配線（v0.22.2 タグ基準）
tests/test_decode.py        # 集計の正確性と異常値・境界値・同時呼び出し・再読込の自動テスト
tests/desktop-match.test.mjs # 表示マッチャー（セッション不一致・接続先混在時 `—`）の依存なしテスト
THIRD_PARTY_NOTICES.md      # 本体パッチが上流派生コードを含むことの明示（著作権表示）
.github/workflows/ci.yml    # 公開 CI（プラグインテスト・Desktop 表示テスト・本体パッチ適用と適用後の計測テスト）
```

プラグイン ID とフォルダ名は `hermes-decode` です（イベント名の名前空間になるため `[a-z0-9_-]{1,64}`、ドット不可）。

## インストール

1. このリポジトリを `~/.hermes/plugins/hermes-decode` に配置します（単一フォルダ。Python 半分と Desktop 半分が同じ folder に入る）。
2. Hermes 設定の有効プラグイン一覧に `hermes-decode` を追加します（`hermes plugins enable hermes-decode`）。これは本体（Python）半分側のスイッチです。
3. Hermes Desktop を起動すると、Desktop 半分がアプリ側のプラグインルートへコピーされ、Capabilities → Plugins の一覧に `hermes-decode` が現れます。Desktop 半分は opt-in（`defaultEnabled: false`）なので、初回はここで項目をオンにします（アプリ側の判断はアプリ側に保存され、設定の有効一覧とは別に切り替わります）。オンにするとステータスバー右側に速度表示が 1 項目だけ現れます。コピー後の更新は再スキャン / 再起動で反映されます。

プラグインを無効にすると、表示項目も `post_api_request` 経由のイベント購読も止まります（追加の後片付けは不要です）。

## 動作条件

- **ストリーミング応答のみ計測対象です。** 非ストリーミング応答、中断されたストリーム、置き換えられたストリーム、失敗した呼び出し、部分応答は未計測となり、窓には入りますが合計へ混ざりません。
- Hermes 本体が `post_api_request` フックへ `decode_seconds`（有限な正の float、または `None`）を渡します。**上流がまだ計測を受け付けていない期間、このリポジトリだけを入れても数値は出ません。** 公表済みの公式 v0.22.2 でも `post_api_request` へ `decode_seconds` は無く、本体パッチ（v0.22.2 基準）を適用しないと速度は出ません。本体パッチを適用するか、本体の对应 PR マージ待ちのリリースを利用してください。切り替え後は本体ビルドインプラグインを有効化するだけで、本体パッチと上流の旧実装を削除できます。

## 本体パッチ（同一内容・二つの基準）

本体側の目的は「デコード秒数を計測し、既存の `post_api_request` へ省略可能な `decode_seconds` として公開する」ことだけに限定しました。ウィンドウ管理・集計・表示・ localization は本体へ持ち込みません。両基準の中身は同一です。

- 上流 main 基準（`patches/decode-hook.patch`）: 基準コミット `cca83848ec79a4a6a2ecc10285725559bf72c97c`、由来（開発元 fork の計測コミット）`c53be73f7afc667a3ab65b8b36d99e0e45798274`。上流 PR 向けで、上流が受け付けた後の `--reverse` はこちらです。
- v0.22.2 基準（`patches/decode-hook-v0.22.2.patch`）: 基準コミット `d923a5eb487a17c0a68801bba9ef0f56c81040a8`（v0.22.2 タグ）。公表済み v0.22.2 を動かしている間だけ使い、上流が計測をマージしたリリースに切り替えたら不要になります。

両基準で計測配線を受ける 7 ファイルのうち 5 ファイル（`agent/codex_runtime.py`、`agent/turn_api_request.py`、`agent/turn_response_intake.py`、両テストファイル）はパッチ生成物がバイト一致、残り 2 ファイルは挿入箇所の周囲のコメント表記が上流側で違うだけの差分です（同一の計測内容）。

```bash

git apply patches/decode-hook.patch           # 適用（上流 main 基準）
git apply --reverse patches/decode-hook.patch # 本体が上流 PR で受け付けた後は元に戻す
git apply --check patches/decode-hook-v0.22.2.patch   # 適用前チェック（v0.22.2 基準）
git apply patches/decode-hook-v0.22.2.patch           # 適用（v0.22.2 基準）
git apply --reverse patches/decode-hook-v0.22.2.patch # v0.22.2 を上流マージ待ちリリースへ切り替える時に元に戻す
```

## 計測と表示の契約（イベント payload）

本体フックから受け取るのは `session_id` / `provider` / `model` / `usage`（正規化済みトークン）/ `decode_seconds`（＋接続 URL `base_url`。URL は不透明な接続先識別子の導出にだけ使い、Desktop へ URL 自身は送らない）だけです。Desktop へ送るのは次に限定します（プロンプト本文・応答本文・reasoning・tool 引数・認証情報・接続 URL・ファイルパス・`usage` 生 dict は送らない）。

| キー | 意味 |
| --- | --- |
| `schema_version` | 契約の版（現状 `1`） |
| `session_id` | Hermes セッション識別子（集計の単位。表示はフォーカス中のセッションに追従する） |
| `provider` | API プロバイダ識別子（情報扱い。表示の照合には使わない） |
| `model` | モデル名（サンプルが自前のモデルを持つ。モデル変更でそのセッションのデコード履歴をリセットし、古い計測を混ぜない。表示側は同じセッションの直近サンプルだけを参照し、main モデルの計測を借りない） |
| `conn` | 不透明な接続先識別子（`base_url` 由来の短いハッシュ。接続 URL は送らない・表出しない。接続先情報が無いときは `null` で、既知の接続先と混在すれば判別不能のまま `—`） |
| `tok_per_sec` | 計測済みの整数速度、未計測なら `null` |
| `measured` | 有効サンプルが窓に在るか |
| `valid_samples` | 窓内の有効サンプル数（整数） |

イベント名は `plugin.hermes-decode.sample`（`broadcast_plugin_event("hermes-decode", "sample", payload)`）。受信側は形が合わない frame を無視し、異常な数値（NaN・無限大・0 以下・文字列）を表示しません。

## Hermes 標準の速度表示との対照

Hermes 標準のステータスバー項目は**フォーカス中のセッション**の直近 10 回の API 呼び出しから `Σ 出力トークン ÷ Σ API 所要時間`（`avg_tps`）を計算し、参照先もセッションごとに切り替わります。当プラグインもセッション単位に戻し、両指標の参照先を揃えました（速度の計算だけデコード専有のままです）。

| 項目 | Hermes 標準（`avg_tps`） | hermes-decode（セッション単位） |
| --- | --- | --- |
| 表示対象 | フォーカス中のセッション | 同じセッション |
| 集計対象 | そのセッションの直近 10 回 | そのセッションの直近 10 回 |
| 計算式 | `Σ 出力トークン / Σ API 所要時間` | `Σ 出力トークン / Σ decode_seconds` |
| プロンプト処理・待機 | 含む | 含まない |
| セッション切替 | 表示対象が切り替わる | 同様に切り替わる |
| 新規セッション | 初回の完了まで `—` | 同様に `—` |
| 他セッションとの共有 | なし | なし |

decode 側の注記: 計測できなかった呼び出し（`decode_seconds = None`）はデコード側の分子・分母に含めないので、同じセッションの直近 10 回でも、両指標が常に完全に同じ呼び出し集合を使うとは限りません。

表示の参照はアプリ標準と同じ `host.state.focusedStoredSessionId`（保存済みセッション ID）に追従します。Python 側フックが渡すのは `agent.session_id` で、基準としてはこの保存済み ID へ直接一致させますが、**コンパクション時の ID 継承と再開時の ID 対応は実機検証していません**（本体チェックアウトが Release 0.22.2 で、チャット起動が公式リリース側の import 時不具合に阻まれるため。下記チャットテストと同じブロッカー）。ID が一致しない場合は参照先がサンプルを見つけられず表示は `—` になり、他のセッションの速度を出すことはしません（fail-closed）。ホストが Desktop 半分へ渡すのは main モデルのスラッグだけで、フォーカス中セッション自身のモデルは SDK 経由では取得できません。そこで表示の絞り込みはセッション単位だけで行い、フォーカス中のタブへ main モデルの計測や他タブの計測を借りる絞り込みはしません（サンプルが自前のモデルを持ち、同一セッションに新しいモデルのサンプルが着くと、そのセッションの古いモデルの行を Desktop 側でも一括で退避し、他セッションの行には触れない）。モデル単位との切替設定は作りません（セッション単位へ一本化）。

## 検証

自動テスト（`python -m pytest tests -q`）:

- `300 tokens / 3 seconds` → `100 tok/s`
- `120/2 + 180/4` → `50 tok/s`（単純平均ではない）
- 未計測サンプルを窓へ混ぜても合計が正しく、11 回目で最古サンプルが除外される
- セッションと実接続先単位の窓が混ざらない（他セッションへは引き継がれず、同じセッションでも 2 つ以上の接続先またぎは接続先ごとに別々）
- モデルを切り替えるとそのセッションのデコード履歴がリセットされる（モデル変更直前の計測を混ざらない。元のモデルへ戻っても古い計測を借りない）。プラグインを再読込すると古いサンプルが一切引き継がれない
- 同時進行の API 呼び出しで窓と LRU の一貫性が保たれること（各窓は計測の直近 10 件ちょうど、窓とモデル管理台帳の保持は上限内）
- `NaN` / 無限大 / `0` 秒 / usage 欠落 / `output_tokens` 欠落で数値を出さない
- 送信 payload が契約キーのみであること（接続先は不透明な識別子で、接続 URL 自身は含まない）、窓の保持が 8 件（セッション・接続先の組、セッションのモデル管理台帳も同じ上限）上限であること、フック登録が `post_api_request` 1 件であること

表示マッチャー・キャッシュのテスト（`node tests/desktop-match.test.mjs`、依存なし）: フォーカス中のセッションに属する直近の計測値だけを出す（フォーカス中セッションのモデルが判知できるときはモデルにも一致させる）、参照セッションが違えば `—`（新しいセッション・他セッションのタブ）、1 つのセッションに 2 つ以上の接続先が混在すれば `—`（既知の接続先へ一致しない速度を借りない）、接続先情報が無いサンプルが単独なら通常どおり表示、接続先情報が無いサンプルと既知の接続先が混在すれば `—`、モデルが判知できないときに他のタブや main モデルの計測を借りない（同じセッションの直近サンプルだけを参照する）、フォーカス中セッションのモデルが判知できるときは他のモデルの窓を借りない、同一セッションへ新しいモデルのサンプル着時で古いモデルの行を一括で退避し他セッションの行には触れない、未計測サンプル着時も同じ、行キャッシュは 8 窓で頭打ち（Python 側の LRU と同じ上限）、参照セッションが無い（`null`・空文字）なら数値を出さない、形が合わない入力・ゴミサンプルで落ちない。

本体側の計測テスト（上流 Hermes のテストスイート、パッチに含まれる）: 各呼び出しのストリーム・試行単位で計測状態が初期化され、最初の delta 受信前や待機後の tool 開始通知が計測を開始しないこと、最初の delta 以降の tool 開始通知が計測を上書きしないこと、Codex 側では生成物を伴わない announce 通知が窓を開けず、実データを伴う delta が窓を開けること、Codex 側の窓は確定したクリーンな完了終端でのみ閉じられ（failed・incomplete・部分応答は `None`）、リクエストの試行時に `_last_api_decode_seconds` がリセットされること、`decode_seconds` の公開が非ストリーミングでは `None`、`0` 以下・非有限値では `None` になること。

- 実行結果: PR 基準コミットのチェックアウトで `tests/agent/test_first_chunk_at_hook.py` と `tests/agent/test_codex_first_event_timing.py` を実行し `26 passed`（Anthropic 配列ストリームのデコード窓テスト 2 件を含みます。`message_stop` まで届いた応答は計測され、EOF で切れた部分応答は `None` のまま）、開発主分支のチェックアウトでデコード・速度表示・ステータスバー関連の既存テストをデセレクション実行して `59 passed`（既存の履歴契約を保持）を確認しました。公開 CI は毎 push で同じ計測テストを適用済みツリーへ実行し、PR 基準コミットのジョブで `26 passed`、v0.22.2 タグコミットのジョブで `9 passed`（クリーンな Python 3.14 環境。core の実行依存はこのバージョンのマーカーから入り、テスト道具は上流の固定版を使います）を確認しました。

実機 E2E（ローカル LLM、llama-swap 経由の llama.cpp 系エンジン）: Desktop の短いチャット 5 件（ストリーミング、`finish_reason = stop`）につき、送信直前にエンジンログの末尾バイト位置を控えておき、その後に追記された行だけを対象に対応付けました（エンジンログの行にはタイムスタンプが無いためバイト位置で切り分け、同一エンジン上の他のリクエスト──別セッションからの長い生成──とはトークン数で区別）。絶対値の速度・秒数・VRAM 使用量はこの環境の実測なので載せず、同一リクエスト間の相対関係だけを載せます。

- 出力トークン数はエンジン側の生成トークン数と完全一致しました。
- `decode_seconds` は常にエンジン生成時間より小さく（96.8%〜99.2%）、窓が終端フレームで閉じていることと一致します。
- 1 件あたりの速度はエンジン側の `tok/s` と最大 3.2% の差（同一リクエスト同士での比較。リクエストをまたいだ平均との比較ではありません）。
- 同じ呼び出しで `ended_at − first_chunk_at` は桁違いに大きく、`decode_seconds` との差が実機で確認できました（プロンプト処理・応答後処理・待ちは窓に入りません）。
- この環境では実行中にエンジンが VRAM 逼迫を繰り返し警告する状態で、生成速度はリクエストごとに大きく揺れました。比較は常に同一リクエストのエンジン行に対して行うため、絶対値の速度はこの場合一貫性検証の一部としてのみ使い、環境特性として要約して載せません。
- 表示側の窓の振る舞いは、旧（プロバイダ・モデル）単位の設計として実機で確認済みです（セッションをまたぐ共有、アプリ公式項目との対照：セッション A のチャット 1 件の後、同じモデルで新しいセッションタブを開くと表示が計測値を引き継ぎ、同じ瞬間の公式項目は空（`—`））。**セッション単位へ切り替えた後の表示動作（参照がフォーカス中セッションに追従し、セッション切り替えで参照が切り替わり、新しいセッションは初回完了まで `—`、モデル変更で履歴がリセット）は実機検証していません。** ブロッカーは下のチャットテストと同じです（本体チェックアウトが Release 0.22.2 で、チャット起動が公式リリース側の import 時不具合に阻まれる）。セッション単位は本体側との契約を変えないプラグイン内完結の変更で、上の自動テストで確定させています。
- 表示項目の確認: 当プラグインの項目はステータスバー右側に 1 件だけ（公式項目と並び、duplicate しない）。アプリ側のスイッチをオフにすると項目だけ消え、オンに戻すと再表示（他の項目・アプリはそのまま）。未計測の呼び出し（非ストリーミング・中断・計測前の本体プロセス）は `measured = false` となり、表示へ数値を出しません。初回表示（チャット前）は `—` になります。これらは本体側の計測配線と項目登録の確認で、セッション単位切替後も変わりません。ホバー説明文はセッション単位仕様へ書き換えました（「フォーカス中のセッションの直近10回の計測値（生成のリアルタイム速度ではない）」）。**新しい文言は実機 tooltip で再検証していません**（旧文言の tooltip 確認は済んでいます）。

## 制約と非目標

- CLI・TUI・組み込み表示には速度を出しません（Desktop 専用）。
- Web ダッシュボード、速度グラフ、時系列解析、履歴 DB、設定 UI、統計・telemetry、他モデルとの比較機能を作りません。
- 表示項目はステータスバー右側の 1 項目だけ（pane・ページ・コマンドを作らない）。
- 上流 Hermes が計測をマージする前、「本体パッチ無しで公式プラグインだけでインストールできる」は要求しません。
