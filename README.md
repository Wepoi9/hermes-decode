# Hermes Decode（Desktop 専用デコード速度プラグイン）

Hermes Desktop のステータスバーに、現在のモデルのデコード速度を1行で表示する単一パッケージの Hermes プラグインです。計測履歴はセッションと実際の接続先ごとに管理し、それぞれ直近10回分の完了呼び出しを保持して、そのうち計測できた分だけを集計します。セッションを切り替えると表示の参照先も切り替わり、新しいセッションでは最初の呼び出しが完了するまで `—` を表示します。表示するのは、現在使用しているセッションの最新の計測値で、他のセッションの値は表示しません。接続先を切り替えた場合も、そのセッションの最新の計測値がそのまま表示対象になります（接続先の識別は集計の内部に留め、表示側へは渡しません）。モデルを切り替えると、そのセッションのデコード履歴をリセットし、切り替え前のモデルの計測値が混ざらないようにします。表示値は完了済みの呼び出しから算出したもので、生成中のリアルタイム速度ではありません。

- 速度の定義：直近10回の完了呼び出しのうち計測できた分について、出力トークン数の合計をデコード時間の合計で割ります（`Σ output tokens ÷ Σ decode seconds`）。各応答の速度を単純平均するものではありません。未計測の呼び出しも窓の 1 枠を占めますが、分子・分母には混ざりません。表示の値は最新の呼び出しのものです。最新の呼び出しを計測できなかったときは `—` を表示し、窓に残った履歴は次の計測できた呼び出しで再利用します。
- 表示は公式項目と同じ表記（⚡ アイコン付きで整数 `… t/s`、例 `⚡ 105 t/s`。丸めは公式項目と同じ四捨五入）。未計測のときは値を出しません（`⚡ —`）。項目はステータスバーの右クリックメニュー（「Show in status bar」）に `デコード速度` として並び、公式速度項目（`Tokens per second`）と同じ仕組みで表示・非表示を切り替えられます（切り替えはアプリ側の設定に保存され、再起動後もそのまま）。
- 計測区間は、そのリクエストで最初の実データの delta を受信した瞬間から、終端フレームの処理が完了するまでです。ストリーミング応答のみを対象とし、待機・ツール実行・プロンプト処理・再試行・中断・失敗／不完全終端を除外します。ツール引数・reasoning の delta はデコード生成の開始点なので、その生成時間は窓に含めます（Codex 側は実データを伴う delta だけを数え、引数なしの announce 通知は窓を開けません）。窓を閉じられるのは確定したクリーンな完了終端だけで、failed・incomplete 終端は `None`（未計測）のままです。
- データは原則としてメモリ内にのみ保存します。履歴は（セッション, 実接続先）単位の窓（セッション横断では共有されない直近 10 件）に保ち、窓の保持は少数（LRU 8 窓、セッションのモデル管理台帳も同じ上限で頭打ち）に保ち、無制限に増やしません。接続先の識別はこのプロセス内の窓の添字としてだけ使い、接続 URL もその派生物もイベントには含めません。永続 DB・ログ・外部 API サーバー・WebSocket サーバー・バックグラウンドポーリングは使いません。窓の読み書きは小さなロックで一貫性を保ち、同時進行の API 呼び出しとプラグイン再読込の両立を確認します。

## 構成

```
plugin.yaml                 # 本体フック post_api_request のみ宣言（ツールは登録しない）
__init__.py                 # 集計（直近10件の窓・合算比）と Desktop へのイベント通知
desktop/plugin.js           # Desktop 表示（STATUSBAR_AREAS.right にメニューで切り替え可能な 1 項目のみ、フォーカス中セッション追従）
patches/decode-hook.patch   # 上流 main の固定基準へ適用する一時的な計測配線
tests/test_decode.py        # 集計の正確性と異常値・境界値・同時呼び出し・再読込の自動テスト
tests/desktop-match.test.mjs # 表示マッチャー・キャッシュ（セッション不一致・未計測時の表示戻し）と二重宣言した上限の一致の依存なしテスト
THIRD_PARTY_NOTICES.md      # 本体パッチが上流派生コードを含むことの明示（著作権表示）
docs/VERIFICATION.md        # 実機 E2E・クラウド実測・パッチ基準追従の日付入り検証記録
.github/workflows/ci.yml    # 公開 CI（プラグインテスト・Desktop 表示テスト・本体パッチを上流 main 基準へ適用して計測テスト）
```

プラグイン ID とフォルダ名は `hermes-decode` です（イベント名の名前空間になるため `[a-z0-9_-]{1,64}`、ドット不可）。

## インストール

1. このリポジトリを `~/.hermes/plugins/hermes-decode` に配置します（単一フォルダに Python 側と Desktop 側のファイルを配置する）。
2. Hermes 設定の有効プラグイン一覧に `hermes-decode` を追加します（`hermes plugins enable hermes-decode`）。これは本体（Python）側の有効化設定です。
3. Hermes Desktop を起動すると、Desktop 半分がアプリ側のプラグインルートへコピーされ、Capabilities → Plugins の一覧に `hermes-decode` が現れます。Desktop 半分は opt-in（`defaultEnabled: false`）なので、初回はここで項目をオンにします（アプリ側の判断はアプリ側に保存され、設定の有効一覧とは別に切り替わります）。オンにするとステータスバー右側に速度表示が 1 項目だけ現れます。表示のみの切り替えはステータスバーの右クリックメニュー（「Show in status bar」）で行います（当項目は `デコード速度`、公式速度項目は `Tokens per second`。公式項目をオフにすれば当プラグインだけで速度を出せます）。コピー後の更新は再スキャン / 再起動で反映されます。

プラグインを無効にすると、表示項目も `post_api_request` 経由のイベント購読も止まります（追加の後片付けは不要です）。

## 動作条件

- **ストリーミング応答のみ計測対象です。** 非ストリーミング応答、置き換えられたストリーム、失敗した呼び出し、部分応答は未計測になります。フックが発行される未計測の呼び出しは窓の 1 枠を占めますが合計へ混ざらず、フック自体が発行されないケース（中断されたターンなど）は窓に入りません。
- Hermes 本体が `post_api_request` フックへ `decode_seconds`（有限な正の float、または `None`）を渡します。**上流がまだ計測に対応していない間、このリポジトリだけを入れても数値は出ません。** 上流 main の先端（基準コミット `145f26b5a5…`、v0.22.5+canary 系）でも `post_api_request` へ `decode_seconds` は渡されず、`agent/turn_response_intake.py` は `first_chunk_at` だけを渡します（基準ツリーを `decode_seconds` / `_last_api_decode_seconds` で走査して 0 件であることを確認済み）。本体パッチ（上流 main 基準）を適用しないと速度は出ません。本体パッチを適用するか、対応する上流 PR がマージされたリリースを利用してください。切り替え後は本体ビルドインプラグインを有効化するだけで、本体パッチと上流の旧実装を削除できます。

## 本体パッチ（1 本の差分・基準は上流 main）

本体側の変更は、デコード時間を計測し、既存の `post_api_request` に省略可能な `decode_seconds` として渡すことだけに限定しています。窓の管理・集計・表示・ローカライズは本体には持ち込みません。

パッチは `patches/decode-hook.patch` の 1 本だけです。git の差分は適用先のコミットを含まないので、基準は次のコミットで指定します（この基準は CI と本節が保持する固定値です）。公開 CI は毎 push でこの基準へ `git apply --check` と適用後の計測テストを実行するので、基準がずれたら CI が止まります。

- 上流 main 基準: 基準コミット `145f26b5a5198f5a733641ef6b6c3d74f087269d`（2026-10-29 に上流 main の先端として固定。`git describe` は `v0.22.5+canary.20261028T064834Z-471-g145f26b5a5`）。前の基準 `0431192d69d4afd2443a7da15bb9e129a424414c` から 426 コミット進んでおり、計測配線の 7 ファイルのうち内容が変わっていたのは `agent/chat_completion_helpers.py` の 1 行（Bedrock の client 生成でモデルを渡す行）だけでした。同じ差分はそのまま新基準へ適用できます（適用と計測テストの実測は `docs/VERIFICATION.md` 2026-10-29 節）。
- 実機のローカルインストール（`main` を追う更新経路）は現時点で前の基準 `0431192d69…` にあり、計測配線は未コミットの作業ツリー変更として入っています。`hermes update` で本体が新基準以降へ進んだら、そのツリーへこの差分を再適用してください。

リリースタグ基準は維持しません。v0.22.5 タグ `bf0203a794…` では `_CodexResponseAssembler` のクラス属性の並びが main と違うため、同じ差分は `agent/codex_runtime.py` で reject します（v0.22.4 タグ基準の差分は retired しました）。公表済みリリースを動かす場合は、そのツリーへ計測配線を移植してから適用してください。

```bash
git apply --check patches/decode-hook.patch   # 適用前チェック（実際に動かしている本体のツリーで）
git apply patches/decode-hook.patch           # 適用
git apply --reverse patches/decode-hook.patch # 本体が上流 PR で受け付けた後は元に戻す
```

`hermes update` は作業ツリーの未コミット変更を autostash して fast-forward します。本体を更新すると計測配線も退避されるので、更新あとは現在のツリーへ差分を再適用します（autostash は pop しません）。次の例では `$pluginRepo` に実際のリポジトリ配置先を入力します。

```powershell
$pluginRepo = Read-Host 'Path to hermes-decode repository'
$hermesRepo = Join-Path $env:LOCALAPPDATA 'hermes\hermes-agent'
$patch = Join-Path $pluginRepo 'patches\decode-hook.patch'
Select-String -Path (Join-Path $hermesRepo 'agent\*.py') -Pattern 'decode_seconds'
git -C $hermesRepo apply --check $patch
git -C $hermesRepo apply $patch
```

`--check` が失敗しただけでは、本体が前進したとは断定できません。まず計測配線がすでに適用済みでないか、作業ツリーに競合する変更がないかを確認してください。未適用で作業ツリーも整理済みなのに失敗する場合は、基準との差分を調べてから計測配線だけを現行コードへ移植し、基準コミットと本節・CI の pin を同時に更新してください（`docs/VERIFICATION.md` の 2026-10-28 節が移植の手順と検証結果の手本です）。

## 計測と表示の契約（イベント payload）

本体フックから受け取るのは `session_id` / `provider` / `model` / `usage`（正規化済みトークン）/ `decode_seconds`（＋接続 URL `base_url`。URL はこのプロセス内の窓の添字としてだけ使い、Desktop へ URL 自身も、その派生物も送りません）だけです。Desktop へ送るのは次に限定します（プロンプト本文・応答本文・reasoning・tool 引数・認証情報・接続 URL・ファイルパス・`usage` 生 dict は送らない）。

| キー | 意味 |
| --- | --- |
| `schema_version` | 契約の版（現状 `2`） |
| `session_id` | Hermes セッション識別子（集計の単位。表示はフォーカス中のセッションに追従する） |
| `provider` | API プロバイダ識別子（情報扱い。表示の照合には使わない） |
| `model` | モデル名（サンプルが自前のモデルを持つ。モデル変更でそのセッションのデコード履歴をリセットし、古い計測を混ぜない。表示側はモデル照合なしでそのセッションの最新サンプルだけを読む：フォーカス中セッションの自前モデルは SDK 経由で取得できないため） |
| `tok_per_sec` | 最新の呼び出しを計測できたときの整数速度。最新の呼び出しを計測できなかったときは `null` |
| `measured` | 最新の呼び出しを計測できたか（`false` のときは `tok_per_sec` も `null`。Desktop 側は表示を `—` に戻す。有効な履歴は Python 側の窓に残るので、次の計測できた呼び出しで集計が再開する） |
| `valid_samples` | 窓内の有効サンプル数（整数。最新の呼び出しが未計測でも履歴の件数は分かる） |

イベント名は `plugin.hermes-decode.sample`（`broadcast_plugin_event("hermes-decode", "sample", payload)`）。受信側は形が合わない frame を無視し、異常な数値（NaN・無限大・0 以下・文字列）を表示しません。契約の版が一致しない frame（旧版と新版の混在）も無視します。

## Hermes 標準の速度表示との対照

Hermes 標準のステータスバー項目は**フォーカス中のセッション**の直近 10 回の API 呼び出しから `Σ 出力トークン ÷ Σ API 所要時間`（`avg_tps`）を計算し、参照先もセッションごとに切り替わります。当プラグインもセッション単位に戻し、両指標の参照先を揃えました（速度の計算だけデコード専有のままです）。表示表記と表示・非表示の切り替えも公式項目と共通です（同じ ⚡ アイコンと `… t/s`、同じ右クリックメニュー）。両方をオンにすると速度が 2 項目並び、右クリックメニューでどちらかをオフにするとその項目だけ消えます（当プラグイン項目の位置は公式項目より外側寄りに並び、公式項目とまったく同じ場所へ差し替えることは現在の SDK では保証しません）。

| 項目 | Hermes 標準（`avg_tps`） | hermes-decode（セッション単位） |
| --- | --- | --- |
| 表示対象 | フォーカス中のセッション | 同じセッション |
| 集計対象 | そのセッションの直近 10 回 | そのセッションの、その接続先の直近 10 回（接続先ごとに別の窓。表示はその窓の最新結果） |
| 計算式 | `Σ 出力トークン / Σ API 所要時間` | `Σ 出力トークン / Σ decode_seconds` |
| プロンプト処理・待機 | 含む | 含まない |
| セッション切替 | 表示対象が切り替わる | 同様に切り替わる |
| 新規セッション | 初回の完了まで `—` | 同様に `—` |
| 他セッションとの共有 | なし | なし |

decode 側の注記: 計測できなかった呼び出し（`decode_seconds = None`）はデコード側の分子・分母に含めないので、同じセッションの直近 10 回でも、両指標が常に完全に同じ呼び出し集合を使うとは限りません。

表示の参照はアプリ標準と同じ `host.state.focusedStoredSessionId`（保存済みセッション ID）に追従します。Python 側フックが渡すのは `agent.session_id` で、基準としてはこの保存済み ID へ直接一致させますが、コンパクション時の ID 継承は 2026-10-16 の実機プロブで確認済みです（圧縮のコミット前後で `session_id` は不変、圧縮後の最初のターンも同じセッション id で完了し、参照先と表示はそのまま継続しました。`docs/VERIFICATION.md`）。ID が一致しない場合は参照先がサンプルを見つけられず表示は `—` になり、他のセッションの速度を出すことはしません（fail-closed）。ホストが Desktop 半分へ渡すのは main モデルのスラッグだけで、フォーカス中セッション自身のモデルは SDK 経由では取得できません。そこで表示はモデル照合をせずセッションの条件だけで読みます（そのセッションの最新サンプルが読める。main モデルのスラッグを別タブの照合に使わない。同一セッションの行は新しいサンプルで置き換わるため、直前のモデルの速度が表示に残りません）。モデル単位との切替設定は作りません（セッション単位へ一本化）。

## 検証

自動テスト（`python -m pytest tests -q`）:

- `300 tokens / 3 seconds` → `100 tok/s`
- `120/2 + 180/4` → `50 tok/s`（単純平均ではない）
- 半端な速度は四捨五入で整数にする（`3 tokens / 2 seconds` の 1.5 → `2`。公式項目の `Math.round` と同じ丸め。切り捨てへの変換はこのテストで検知する）
- 未計測サンプルを窓へ混ぜても合計が正しく、11 回目で最古サンプルが除外される
- 最新の呼び出しを計測できなかったときは速度を返さない（`measured` が偽で `tok_per_sec` は `null`）。窓に残った履歴は次の計測できた呼び出しで再利用される
- セッションと実接続先単位の窓が混ざらない（他セッションへは引き継がれず、同じセッションでも 2 つ以上の接続先またぎは接続先ごとに別々）
- モデルを切り替えるとそのセッションのデコード履歴がリセットされる（モデル変更直前の計測値が混ざらない。元のモデルへ戻っても古い計測を借りない）。プラグインを再読込すると古いサンプルが一切引き継がれない
- 同時進行の API 呼び出しで窓と LRU の一貫性が保たれること（各窓は計測の直近 10 件ちょうど、窓の保持は上限内で、ワーカースレッドでの失敗は親へ回収して報告する）
- `NaN` / 無限大 / `0` 秒 / usage 欠落 / `output_tokens` 欠落で数値を出さない
- 送信 payload が契約キーのみであること（接続先・プロセス世代・接続 URL はいずれも含まれない）、窓の保持が 8 件（セッション・接続先の組）上限で、退避されたセッションの次の呼び出しが新しい窓から始まること、フック登録が `post_api_request` 1 件であること

表示マッチャー・キャッシュ・payload 解釈のテスト（`node tests/desktop-match.test.mjs`、依存なし）:

- フォーカス中のセッションに属する行だけを出す（モデル照合はしない。ホストがフォーカス中セッションの自前モデルを渡さないため、モデルで絞り込まずそのセッションの最新行を読む。行はモデルを持たない）
- 参照セッションが違えば `—`（新しいセッション・他セッションのタブ）
- 同じセッションの行は常時 1 行だけ保持され、接続先を切り替えた直後でも表示は `—` にならない（切り替えはただそのセッションの行を置き換える）
- 新しいサンプルはそのセッションの行を置き換え、他セッションの行は触れない
- 未計測のサンプルが着たらそのセッションの行が消えて表示は `—` へ戻る（履歴は Python 側の窓に残るので、次の計測できた呼び出しで復帰する）
- 行キャッシュは 8 セッションで頭打ち（Python 側の窓 LRU と同じ数だが単位は違う。Python は（セッション, 実接続先）窓を 8 窓、Desktop はセッション行を 8 行保つ）
- 参照セッションが無い（`null`・空文字）なら数値を出さない
- payload の解釈: `measured` が偽なら表示を戻し、契約の版がちがう frame・`provider` / `model` 欠落・使える速度や件数にならない frame は無視する。形が合わない入力・ゴミサンプルで落ちない
- Python 側と Desktop 側が二重宣言している上限（窓 10 件・保持 8 件・payload 版 `2`）がまだ一致していること（両半分は互いに import できないため、ここがズレの検知点。数値の一致を見ており、キーや型の完全一致まではこのテストでは保証しない）
- 表示項目の登録方式は同じファイルの構造検査（`render` は `data` 内に 1 個だけ・トップレベルの `render` を置かない・メニューへ並ぶ項目名を持ち、公式項目と同じアイコン・`… t/s` 表記を出す。イベント購読が plugin id の名前空間のイベント名を使っていることも確認する。SDK 経由の登録と描画そのものは実機 E2E 側で確認済み）

本体側の計測テスト（上流 Hermes のテストスイート、パッチに含まれる）: 各呼び出しのストリーム・試行単位で計測状態が初期化され、最初の delta 受信前や待機後の tool 開始通知が計測を開始しないこと、最初の delta 以降の tool 開始通知が計測を上書きしないこと、Codex 側では生成物を伴わない announce 通知が窓を開けず、実データを伴う delta が窓を開けること、Codex 側の窓は確定したクリーンな完了終端でのみ閉じられ（failed・incomplete・部分応答は `None`）、リクエストの試行時に `_last_api_decode_seconds` がリセットされること、`decode_seconds` の公開が非ストリーミングでは `None`、`0` 以下・非有限値では `None` になること。Codex 側は決定論的な mock `time.monotonic()`（事前に用意した進行列で時計を進め、実待ちを一切挟まない。列が尽きたあとは最後の刻みを返し、テスト後の teardown で `time.monotonic()` を呼ぶ環境側の後始末を壊しません）で動き、chat 側の窓テストは chunk の間に実際の待機時間（50 ms 以上）を挟んで実際のデコード窓を作ります（Windows では直前・直後の 2 回の読みが同一 tick に潰れることがあり、応答が即座に揃うタスクでは窓が 0.0 秒＝未計測になるため）。

## 制約と非目標

- CLI・TUI・組み込み表示には速度を出しません（Desktop 専用）。
- Web ダッシュボード、速度グラフ、時系列解析、履歴 DB、設定 UI、統計・telemetry、他モデルとの比較機能を作りません。
- 表示項目はステータスバー右側の 1 項目だけ（pane・ページ・コマンドを作らない）。
- 上流 Hermes が計測をマージする前、「本体パッチ無しで公式プラグインだけでインストールできる」は要求しません。
